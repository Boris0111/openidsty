# technical-document-tracking Specification

## Purpose

讓研究者追溯技術論述所依據的特定文件、版本與章節，並分辨已核對研究與新取得文件。文件更新先保存為待核對候選，來源故障與重複取得不會改寫研究或製造新的技術進展。

## Requirements

### Requirement: 技術文件身分與證據範圍可追溯

每份技術文件 MUST 有穩定識別、可解析來源、發布機構、標題、原始位址、文件性質、版本或明示未知、發布精度、取得及查核時間、適用環節／題材。引用 MUST 指向特定版本與章節或定位資訊，並說明支持的論述及範圍；僅讀公開摘要時 MUST 明示未讀全文。

#### Scenario: 引用有版號的介面規格
- **WHEN** 研究使用特定版本的介面要求支持技術論述
- **THEN** 讀者可回溯文件版本、章節、必要摘錄及適用條件
- **AND** 取得時間與發布時間分開，未知發布日不以取得日補造

#### Scenario: 只能讀到公開說明頁
- **WHEN** 發布機構提供說明但全文須申請或目前無法取得
- **THEN** 顯示實際可讀範圍及限制，論述只引用已讀內容
- **AND** 不宣稱已核對完整規範或將摘要當成規範條文

### Requirement: 文件性質與商業證據分開

系統 MUST 區分正式規範、草案、路線圖、廠商說明及其他技術說明，並與研究的證據程度、客戶採用、訂單及收入分開。發布機構名稱、規範發布或 roadmap 時間 MUST NOT 自動使論述變成已核實採用或完成商業化里程碑。

#### Scenario: 路線圖列出未來技術目標
- **WHEN** 新取得的 roadmap 列出預期規格與時間
- **THEN** 顯示為路線圖預期及其適用範圍
- **AND** 題材狀態、里程碑確認與公司受惠判斷維持原核對基準

### Requirement: 新文件版本先進入待核對狀態

新發現版本或可辨認的實質內容變更 MUST 先建立待核對候選，保存前後版本、差異依據及受影響引用。只有維護者核對並提交具查核日期、採納或不採納原因的研究基準後，系統才可投影更新後研究。公開介面 MUST 保持唯讀。

#### Scenario: 發布新的正式版
- **WHEN** 監測發現研究仍引用舊版本而官方提供新版
- **THEN** API 與維護報告保留已核對版本與待核對新版，原研究及引用仍可閱讀；一般閱讀只呈現被引用的已核對範圍，不展示待核對佇列
- **AND** 自動取得流程不修改 Markdown、判讀版本或里程碑核對

#### Scenario: 核對後認定不影響研究
- **WHEN** 維護者核對新版並記錄不採納原因
- **THEN** 候選保留處理紀錄，研究內容與既有判讀版本不產生假變更

### Requirement: 重複取得與頁面雜訊不製造版本

相同文件的同一版本與相同正規化內容 MUST 冪等保存。僅取得時間、HTTP metadata、排版或索引頁無關區塊改變 MUST NOT 新增研究版本或重複待核對候選。解析不確定時 MUST 顯示需人工檢視，不得宣稱已確認新正式版本。

#### Scenario: 連續重跑與索引雜訊
- **WHEN** 連續兩輪取得相同文件，只有最後取得時間或索引頁導覽改變
- **THEN** 更新操作紀錄且不增加文件實質版本、候選或題材更新提示

#### Scenario: 同位址內容改變但無版號
- **WHEN** 文件主體改變且未提供明確版號
- **THEN** 保存可回溯的內容觀測並標為待人工檢視
- **AND** 不合成官方版號、不覆寫已核對版本

### Requirement: 來源故障保留已核對研究

文件監測 MUST 限定於可讀公開範圍並限制取得量；失敗 MUST 與最後成功、人工查核及更新候選分開。403、404、逾時、登入頁或部分解析失敗 MUST NOT 刪除既有文件紀錄、摘錄及研究引用，也不得建立沒有內容依據的新版本。

#### Scenario: 已引用來源改為不可讀
- **WHEN** 原文件取得失敗或導向登入頁
- **THEN** 仍可讀已保存的必要摘錄、版本與研究，維護流程另保留失敗類型及最後成功時間，不在一般閱讀中插入診斷
- **AND** 其他來源及一般網站讀取繼續運作
