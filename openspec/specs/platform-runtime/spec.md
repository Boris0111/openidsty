# platform-runtime Specification

## Purpose

提供可重現的本機開發及自架執行環境，讓產業資訊網站、資料庫與每小時資料流程能一致初始化、持續更新、保留資料並透過操作文件維護，而不影響同機其他專案。

## Requirements

### Requirement: 可重現啟動與持久化

系統 MUST 提供容器設定、環境變數範例、資料庫遷移與研究初始化；停止／重啟 MUST 保留資料。讀者 API MUST 維持唯讀語意，管理寫入 MUST 使用獨立授權邊界；資料庫、Git 編輯空間與流程管理介面預設只在本機或內部可達。動態服務（資料庫、API、網站、排程與讀者入口）本版供本機及私人網路使用，讀者入口不得轉送管理路徑；對網際網路公開的只有不含伺服器的已發布研究靜態快照。

#### Scenario: 新環境與重啟
- **WHEN** 維護者依 README 啟動並重啟服務
- **THEN** 可開啟產業圖，資料庫保留既有事件，其他專案服務不受影響

#### Scenario: 公開版不開放動態服務
- **WHEN** 維護者部署公開靜態快照
- **THEN** 資料庫、API、網站、排程與讀者入口的連接埠仍只綁本機或私人網路，公開版不需要連到任何一項

### Requirement: 每小時排程獨立執行

資料流程 MUST 每小時嘗試更新，並獨立於公開 API worker 運作。重啟或重複觸發 MUST 不造成重複入庫；同一輪任務不得併發執行。

#### Scenario: API 重啟與排程
- **WHEN** API 服務重啟或增加 worker
- **THEN** 不額外建立排程，資料流程可繼續運作

### Requirement: 開發與維護操作可驗證

README MUST 提供前後端開發、容器啟動與停止、單次資料更新、測試、日誌、來源狀態、備份還原、正式服務部署與回退、部署紀錄查詢及公開部署步驟；專案 MUST 提供 dev server 啟動設定。

#### Scenario: 執行單次更新與備份
- **WHEN** 維護者依文件執行更新、備份與還原
- **THEN** 能查詢更新結果，且在獨立還原環境核對資料，不覆寫其他專案

#### Scenario: 依文件部署與回退
- **WHEN** 維護者依文件把一個主線提交部署到正式服務，之後回退到前一版
- **THEN** 每一步都有對應指令與預期結果，部署紀錄可查到兩次操作的提交、備份與 smoke 結果

### Requirement: 版本控制內容可完整重現公開入口

專案 MUST 僅憑版本控制的乾淨 checkout 與文件中的本機設定重現公開入口；忽略規則不得排除必要應用原始碼。自動檢查 MUST 驗證地圖、後端離線測試、前端型別／建置及主要導覽，與真實外部來源擷取分開；正式 runtime 不得載入測試 fixtures。

#### Scenario: 資料覆蓋頁與產物同名
- **WHEN** 乾淨 checkout 建置網站並開啟資料覆蓋入口
- **THEN** 該頁原始碼在版本控制中，入口可載入，測試 coverage 產物仍可忽略

### Requirement: 來源配置與恢復結果可驗證

維護文件 MUST 提供 SEC 真實聯絡設定、官方來源失敗分類、單來源重試及結果核對方法。缺少配置與 HTTP／解析失敗 MUST 分開顯示；無法恢復的來源 MUST 保留既有資料及實際限制。配置與恢復不得重置其他服務或以外殼回應宣稱成功。

#### Scenario: SEC 尚未設定且官方 IR 持續封鎖
- **WHEN** 維護者檢查未配置的 SEC 與回傳 HTTP 403 的 IR
- **THEN** 可辨識各自處理方式，重試仍失敗時留下來源限制，其他來源及研究仍可使用

### Requirement: 一般讀取有界且保留既有資料語意

常用 API MUST 只回傳請求所需的分頁或樣本，總數與筆數限制 MUST 在取得結果前生效；結果 MUST 保持原分類、日期、期別、修訂與排序定義。覆蓋摘要 MUST 不因加入較舊歷史就返回全部原始事件或觀測。效能最佳化 MUST 不截斷影響候選、隱藏未知日期或把缺少資料變成零。

#### Scenario: 增加歷史觀測與事件
- **WHEN** 資料庫累積更多舊事件及指標修訂
- **THEN** 摘要維持有界回應，分頁總數及最新有效修訂正確
- **AND** 同一資料快照上的 30／90 日計數、直接分類與既有樣本定義不變

### Requirement: 快取可重新取得且新鮮度有界

快取 MUST 依資源、研究版本及完整查詢參數隔離，並依資料性質區分：manifest 與未指定研究版本的查詢 MUST 取得目前已發布版本，不保存成功快取；指定已發布版本的研究、目錄、圖、公司比較與固定引用內容不可變，可長期快取，新版本使用不同 key；指標、事件及觀察即使指定研究版本仍屬動態資料，快取 MUST 不超過 60 秒；覆蓋、來源狀態與收藏更新查詢 MUST 可重新取得，管理及身分回應 MUST NOT 進入共用快取。新鮮度上限指相對系統已入庫或已發布資料的讀取延遲，不代表官方來源發布後即在該時間內更新。

重新取得 MUST 可略過快取；失敗回應 MUST 不被保存為正常資料。背景頁、斷線或更新失敗時 MAY 保留最後成功內容並提示；閱讀中發現新研究版本 MUST 先通知，由讀者決定切換。顯示舊快照時 MUST 不以伺服器較新 token 將使用者未讀內容標已讀。

#### Scenario: 更新後重新取得
- **WHEN** 發布新研究版本或新增觀測後，讀者重新取得資料
- **THEN** 未指定版本的查詢取得新版本；已固定舊版的頁面先提示，接受後才整頁切換
- **AND** 動態數值在約定新鮮度內反映已入庫資料，收藏已讀基準仍對應實際看到的回應

#### Scenario: 請求失敗後重試
- **WHEN** 來源狀態或 API 請求曾失敗後恢復
- **THEN** 重試可取得恢復狀態，不被快取的錯誤或其他查詢資料遮蔽

#### Scenario: 公司比較隨研究版本快取
- **WHEN** 讀者以同一研究版本重複開啟相同公司組合的比較
- **THEN** 比較內容可重用長期快取；新研究版本使用不同的快取 key，不沿用舊版比較

### Requirement: 小群讀取效能以可重現基準驗收

系統 MUST 在記錄的本機隔離環境，以固定的真實資料快照及擴大測試資料兩組、10 位同時讀取者、暖機及固定查詢分布量測，並同時運行到期資料更新。驗收目標 MUST 為暖機後每個常用 API 的 p95 < 500ms、覆蓋摘要 p95 < 1 秒且無非預期錯誤；MUST 公開硬體、服務設定、資料規模、各 endpoint 樣本數與延遲、冷讀結果、錯誤、快取狀態及限制。測試資料 MUST NOT 寫入正式資料庫或冒充正式研究；未量測或未達標時不得宣稱容量已保證，快取或其他功能完成不代表效能目標已達成。

#### Scenario: 相同環境比較改善前後
- **WHEN** 在兩組資料上執行固定工作負載並同時運行到期更新
- **THEN** 記錄各 endpoint 分布與延遲、錯誤及快取狀態，可與同環境先前基準比較
- **AND** 包含從網站同網域 proxy 到 backend 的路徑，不只量測前端記憶體命中

#### Scenario: 測量未達目標
- **WHEN** 任一常用 endpoint 的 p95 未達目標或有非預期錯誤
- **THEN** 記錄瓶頸與未通過結果，繼續修正既有讀取流程或明列尚未完成
- **AND** 不以其他 endpoint 的平均值、降低併發或增加未授權基礎設施掩蓋

### Requirement: 文件更新隔離且重啟不製造更新

新增文件投影與監測 MUST 以 additive 方式保留原研究、事件、觀測、判讀版本及此裝置關注契約。監測 MUST 與公開讀取隔離，遵守現有排程防重疊規則。來源部分失敗、重跑、API／worker／DB 重啟 MUST 不製造假文件版本、研究版本或更新提示。

#### Scenario: 部分失敗後重跑並重啟
- **WHEN** 一個文件來源失敗、另一個成功，隨後重跑並重啟服務
- **THEN** 已成功內容、原研究與歷史保持可讀，相同內容不重複建立候選或版本
- **AND** 每個來源保留各自操作狀態，公開 API 不直接呼叫外部文件來源

### Requirement: 新舊開發環境相互隔離

正式研究服務 MUST 使用獨立的容器 project、image、network、資料庫、volumes 與執行憑證，並占用原服務的讀者 origin（web `127.0.0.1:3010`、API `127.0.0.1:8010`、Prefect `127.0.0.1:4201`）；原服務 MUST 保留可回復的 image 與資料，但 MUST NOT 與正式研究服務同時運行。任何會啟動、替換或回退正式研究服務的操作，包括啟用排程，MUST 先確認原服務沒有任何容器在運行、目標 port 未被占用，否則拒絕並說明原因，不得自動停止或刪除原服務。還原演練環境 MUST 使用自己的 project 與 port，不得占用正式 port。還原／遷移只在明確指定的研究資料庫執行；Git 分支回退不得被視為已還原資料庫。

#### Scenario: 預覽新版並保留原服務
- **WHEN** 啟動、重建或停止正式研究服務或還原演練環境
- **THEN** 原服務的容器、image、資料與連線保持原狀

#### Scenario: 原服務仍在運行時啟動正式服務
- **WHEN** 原服務仍有容器在運行或 3010／8010／4201 被占用，並嘗試啟動正式研究服務
- **THEN** 操作拒絕並指出占用者，原服務的容器、image、資料與連線保持原狀

#### Scenario: 原服務仍在運行時啟用排程或回退
- **WHEN** 原服務仍有容器在運行或共用 port 被占用，維護者嘗試啟用正式研究服務的排程，或回退正式研究服務
- **THEN** 操作在改變任何狀態前拒絕並指出占用者，兩邊不會同時抓取官方來源

#### Scenario: 在原 origin 閱讀
- **WHEN** 讀者在切換後開啟 `http://127.0.0.1:3010` 的舊 ticker 深連結、舊題材網址或含 `#candidates` 的連結
- **THEN** 由正式研究服務回應並解析到對應頁面，`#candidates` 轉到「數據與追蹤」，同一 origin 的 v1 題材收藏只遷移一次且 v1 原值保留

#### Scenario: 回復原服務
- **WHEN** 停止正式研究服務並以原 image 啟動原服務
- **THEN** 原服務使用原資料回到 3010，正式研究服務的 volumes 保留，不執行 destructive downgrade

### Requirement: 版本化讀取與有界請求

新版讀取介面 MUST 與 legacy 契約並存，研究回應可固定已發布版本，動態數據標示資料時點。清單與圖形查詢 MUST 有數量及深度界線，回應截斷需明示；相同請求可合併，管理及身分回應不得共用快取。發布或還原後不得混用不同研究版本的內容。

#### Scenario: 大型關係查詢
- **WHEN** 查詢關係數超過單次限制
- **THEN** 回應明示截斷並提供繼續探索方式，請求不無限遍歷或耗盡資源

### Requirement: 故障可恢復且不偽裝新鮮度

來源失敗 MUST 保留最後有效資料，發布失敗 MUST 保留舊研究；資料庫不可用時 MUST 回傳可重試的服務不可用狀態，不假造空資料成功。系統 MUST 定期備份資料庫、排程元件自己的資料庫、研究 Git 歷史與資產，並能在獨立環境核對還原；排程元件升版之前的部署前備份 MUST 保留為回退邊界，例行清理 MUST NOT 刪除它。祕密設定不得隨公開研究或收藏備份流出。

#### Scenario: 資料庫故障
- **WHEN** 讀取 API 無法連線資料庫
- **THEN** 回傳服務不可用及請求識別，畫面保留已成功載入的內容並說明目前無法更新

#### Scenario: 隔離還原演練
- **WHEN** 維護者從備份建立新的還原環境
- **THEN** 能核對正式研究版本、歷史、數值修訂與資產，不覆寫原資料庫

#### Scenario: 備份涵蓋排程元件的資料庫
- **WHEN** 每日備份或部署前備份完成
- **THEN** 備份含排程元件自己的資料庫，並記錄它的遷移版本與排程、執行紀錄的筆數
- **AND** 在獨立還原環境還原後，遷移版本與筆數和備份記錄相符

#### Scenario: 排程元件升版後要回到舊版
- **WHEN** 某次部署升級了排程元件，之後維護者需要回到升級前的版本
- **THEN** 回退被拒絕，並指出升級前的部署前備份；這份備份仍在，同時含研究資料庫與排程元件的資料庫，可依事故程序還原

#### Scenario: 較舊的備份沒有排程元件的資料庫
- **WHEN** 從本規則生效前的備份建立還原環境
- **THEN** 研究資料照常還原與核對，報告註明這份備份沒有排程元件的資料庫

### Requirement: 排程在重啟後自動恢復

正式研究服務的排程中樞與執行 worker MUST 與資料庫、API、網站採用相同的自動重啟策略：Docker 或主機重啟後，已啟用的排程 MUST 自動恢復，不需要維護者重新手動啟動。一次性的部署設定服務 MUST NOT 自動重複執行。被維護者手動停止的服務（包括原服務）MUST 在重啟後維持停止，不得因自動恢復而與研究服務同時占用共用 port。服務設定檢查 MUST 拒絕缺少自動重啟策略的常駐排程服務。

#### Scenario: 主機重開機後排程自動恢復
- **WHEN** 排程已啟用的研究服務所在主機重開機，Docker 重新啟動
- **THEN** 排程中樞與 worker 自動回到運行狀態，下一個每小時時段照常執行，不必重新以排程 profile 啟動

#### Scenario: 排程中樞比 worker 晚就緒
- **WHEN** 重啟時 worker 先啟動，排程中樞或資料庫尚未就緒，導致 worker 結束
- **THEN** worker 依重啟策略重試，直到連上排程中樞；部署設定服務不重複執行，也不建立重複排程

#### Scenario: 原服務維持停止
- **WHEN** 原服務在切換時已被手動停止，之後主機重開機
- **THEN** 原服務維持停止，研究服務的共用 port 不發生衝突

#### Scenario: 設定缺少重啟策略
- **WHEN** 研究服務設定中的排程中樞或 worker 未設定自動重啟策略
- **THEN** 服務設定檢查失敗並指出該服務，不啟動研究服務

### Requirement: 自動檢查與 runtime 一致

自動檢查 MUST 使用與 runtime image 相同的鎖定 Python 依賴版本，不得在檢查時解析出不同的間接依賴。測試 fixtures 在任何平台 checkout 後 MUST 與版本控制中的位元組內容一致，不得因換行轉換改變內容或雜湊。版本控制中的 runtime 與維運腳本測試 MUST 納入自動檢查，包括研究服務的部署、回退與資料庫遷移分類規則；需要 Docker、真實資料庫或外部來源的檢查仍與自動檢查分開。

#### Scenario: Windows checkout 執行雜湊測試
- **WHEN** 在預設會轉換換行的 Windows checkout 執行依賴 fixture 雜湊的離線測試
- **THEN** fixture 位元組與版本控制內容相同，測試結果與 Linux checkout 一致

#### Scenario: 間接依賴發布新版
- **WHEN** 某個未直接鎖定的間接依賴在套件庫發布新版
- **THEN** 自動檢查仍安裝 runtime 使用的版本，不因新版而產生與 runtime 不同的結果

#### Scenario: 維運腳本測試
- **WHEN** 有人修改研究服務的啟動、互斥、設定檢查、部署或回退腳本，或新增資料庫遷移
- **THEN** 自動檢查執行對應的測試，不需要 Docker 也能驗證設定規則、部署順序、回退的拒絕條件與遷移分類

### Requirement: 自動檢查不因時序偶發失敗

自動檢查對畫面狀態、版面尺寸或網路請求等非同步結果的判定 MUST 等待結果穩定，或在有界的時間內重試後才判定成功或失敗；同一份程式碼在相同環境重跑時 MUST 得到相同結果。自動檢查 MUST NOT 以整體重跑或自動重試來掩蓋偶發失敗，真正的回歸仍須在第一次執行就失敗。

#### Scenario: 縮放視窗後檢查溢出
- **WHEN** 檢查在改變視窗大小後立即判定頁面有沒有水平溢出
- **THEN** 檢查等待版面穩定後才判定，不因量測時機落在重新繪製之前而失敗

#### Scenario: 隱藏頁面後檢查請求數
- **WHEN** 檢查在頁面隱藏前觸發了請求，接著驗證隱藏期間不再發出請求
- **THEN** 檢查以隱藏前請求全部抵達後的數量作為基準，不把已發出的請求算成隱藏期間的請求

#### Scenario: 真正的溢出回歸
- **WHEN** 某次修改讓頁面在手機寬度持續水平溢出
- **THEN** 檢查在等待時限後失敗，CI 不會因重試而轉為通過

### Requirement: 正式服務只執行已合併提交的版本化 image

正式研究服務 MUST 只執行由主線（`main` 的第一父鏈）上的提交、直接自版本控制內容建置的 image；每個 image MUST 標示來源提交，每個運行容器的 image 與提交 MUST 可查詢並與部署紀錄一致。開發用 checkout 的分支切換、未提交修改與測試檢查 MUST NOT 改變正式服務的 image、容器、祕密、備份或排程。會改變正式服務的操作 MUST 只在指定的部署目錄、工作目錄乾淨且版本與部署紀錄一致時執行，否則拒絕並說明原因；正式資料庫已存在時 MUST NOT 產生新的執行祕密。

#### Scenario: 開發 checkout 切換分支
- **WHEN** 維護者或 agent 在開發 checkout 切換分支、留下未提交修改，並執行測試與檢查
- **THEN** 正式服務的 image、容器、祕密、備份與排程都不變

#### Scenario: 部署未合併的提交
- **WHEN** 要部署的提交不在 `main` 的第一父鏈上，例如未 merge 的分支或 PR 內部的中間提交
- **THEN** 部署拒絕並說明原因，正式服務維持原版本

#### Scenario: image 內容與版本控制一致
- **WHEN** 從某個提交建置正式 image
- **THEN** image 內的專案檔案與該提交的版本控制內容逐位元組相同，不受換行轉換或未追蹤檔案影響
- **AND** image 標示來源提交、資料庫遷移的最新版本與其中的收縮遷移

#### Scenario: 在部署目錄外操作正式服務
- **WHEN** 在部署目錄以外、部署目錄有未提交修改或未追蹤檔案，或其版本與部署紀錄不一致時，執行會改變正式服務的操作
- **THEN** 操作拒絕並指出不符合的條件，正式服務不變

#### Scenario: 缺少正式祕密時不產生新祕密
- **WHEN** 正式資料庫的 volume 已存在，而執行位置沒有正式祕密設定
- **THEN** 操作拒絕，不產生與既有資料庫不符的新祕密

#### Scenario: 查詢運行版本
- **WHEN** 維護者查詢正式服務狀態
- **THEN** 列出每個運行容器的提交與 image、資料庫遷移版本與最近一次部署紀錄，並指出不一致之處

### Requirement: 部署與回退先備份並留有紀錄

每次部署與回退 MUST 先完成可核對的備份，並在只追加的部署紀錄寫入一筆，包含提交、image、遷移版本前後、備份位置、smoke 結果與成敗。部署 MUST 在新版本的初始化成功後才替換服務，並替換所有運行中的應用服務。smoke 失敗時 MUST 記錄並回報可執行的回退方式，或說明為何只能還原備份，不自動回退。回退 MUST NOT 重新執行初始化；跨越收縮遷移或排程元件版本時 MUST 拒絕並指向備份還原。部署、回退與每日備份 MUST NOT 同時執行。

#### Scenario: 標準部署
- **WHEN** 維護者部署一個主線提交
- **THEN** 先完成備份，新版本初始化成功後才替換 API、網站與運行中的排程服務
- **AND** smoke 檢查結果、每個服務的 image 與遷移版本寫入部署紀錄

#### Scenario: 新版本初始化失敗
- **WHEN** 新版本的資料庫遷移或研究初始化失敗
- **THEN** 原版本的服務繼續回應讀者，部署紀錄寫入失敗原因

#### Scenario: 部署後 smoke 檢查失敗
- **WHEN** 服務已替換，但健康檢查、已發布研究版本或頁面檢查不通過
- **THEN** 部署紀錄標示失敗，並列出可直接執行的回退指令，或說明因收縮遷移只能還原備份
- **AND** 系統不自動回退

#### Scenario: 回退到只差擴充遷移的前一版
- **WHEN** 維護者回退到部署紀錄中前一個成功版本，兩者之間只有擴充遷移
- **THEN** 回退不執行初始化與地圖重新匯入，不因舊版不認得較新的遷移版本而失敗，也不新增判讀版本
- **AND** smoke 通過後寫入部署紀錄

#### Scenario: 回退跨越收縮遷移或排程元件版本
- **WHEN** 回退的目標版本與目前資料庫之間有收縮遷移，或兩者的排程元件版本不同
- **THEN** 回退拒絕，指出原因及作為回退邊界的部署前備份

#### Scenario: 部署時有資料更新正在執行
- **WHEN** 部署開始時排程中的資料更新仍在執行，或每日備份正在進行
- **THEN** 部署拒絕或等待鎖釋放，不與它們同時寫入；維護者明確強制時才中斷正在執行的資料更新

### Requirement: 資料庫遷移區分擴充與收縮

每個資料庫遷移 MUST 屬於擴充（前一版程式可在新 schema 上運作）或收縮（移除、改名、收窄既有結構或刪除資料）。含破壞性語句的遷移 MUST 標記為收縮，或附上前一版不受影響的審查理由；自動檢查 MUST 拒絕未標記者，並 MUST 要求遷移鏈線性且只有一個 head。收縮遷移 MUST 在前一個已部署版本不再使用被移除的結構後才部署，部署時 MUST 明確確認，該次部署前備份為回退邊界且 MUST NOT 被例行清理刪除。已合併的遷移 MUST NOT 刪除或改寫，撤回以新的遷移進行。

#### Scenario: 新增未標記的破壞性遷移
- **WHEN** 有人新增含刪除資料表、欄位、政策或資料，或改名、收窄型別的遷移，但未標記
- **THEN** 自動檢查失敗，指出檔案與語句

#### Scenario: 經審查的擴充遷移
- **WHEN** 遷移只新增結構，或含可疑語句但已附上前一版不受影響的理由
- **THEN** 自動檢查通過，該遷移不構成回退邊界

#### Scenario: 部署含收縮遷移
- **WHEN** 要部署的版本相對目前資料庫新增收縮遷移，而維護者未明確確認
- **THEN** 部署拒絕並列出收縮遷移
- **AND** 明確確認後部署，該次部署前備份標示為回退邊界，例行清理不刪除它

#### Scenario: 遷移鏈分岔
- **WHEN** 兩個遷移宣告同一個前一版本，或遷移編號與檔名不一致
- **THEN** 自動檢查失敗並指出衝突的遷移

### Requirement: 合併前實機驗證在演練環境進行

需要實機的合併前驗證 MUST 在獨立的演練環境進行，MUST NOT 讓正式服務執行未合併的程式碼。演練 MUST 先以備份記錄的基準 image 從最新正式備份還原，再以待合併提交的 image 預演部署與回退，並核對資料差異。分支程式的資料庫契約檢查與重建檢查 MUST 只寫入演練環境的資料庫與 volume。演練 MUST 可從任何 checkout 或 worktree 執行而不讀取正式祕密，錯誤輸出 MUST 遮蔽演練祕密。只有正式環境才有的行為於合併後部署時核對並記錄。

#### Scenario: 預演 PR 的部署
- **WHEN** 維護者從 PR 的 worktree，以最新正式備份還原演練環境，再部署 PR 提交的 image
- **THEN** 演練以與正式部署相同的步驟完成初始化與 smoke 檢查，報告列出資料表的變動與遷移版本
- **AND** 正式服務的 image、容器、資料與祕密都不變

#### Scenario: 待合併版本含新遷移
- **WHEN** PR 新增資料庫遷移，維護者從正式備份還原演練環境
- **THEN** 還原使用備份記錄的基準 image 而成功，新遷移只在預演部署時套用

#### Scenario: 預演回退
- **WHEN** 預演部署後回退到基準 image
- **THEN** 只差擴充遷移時回退通過 smoke 檢查；跨越收縮遷移時回退被拒絕，與正式環境的規則相同

#### Scenario: 從 worktree 執行演練
- **WHEN** 在沒有正式祕密的 worktree 執行演練，且某個步驟失敗
- **THEN** 演練不讀取正式祕密，錯誤輸出中的演練祕密已被遮蔽

#### Scenario: 分支程式的資料庫檢查
- **WHEN** 以分支程式執行需要 PostgreSQL 的契約檢查或研究重建檢查
- **THEN** 檢查只寫入演練環境的資料庫與 volume，正式資料庫 cluster 與 volume 不變
