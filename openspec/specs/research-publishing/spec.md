# research-publishing Specification

## Purpose

讓單一維護者能透過網站表單或既有 agent 的檔案編輯維護同一份研究，經預覽、差異檢查及驗證後發布可追溯版本。讀者只會取得完整且已發布的研究，草稿、維護診斷與發布失敗不影響既有閱讀內容。

## Requirements

### Requirement: 表單與檔案共用研究草稿

系統 MUST 接受結構化表單加 Markdown 內文，以及檔案匯入兩種編輯方式；兩者 MUST 使用相同 Schema、引用規則及發布流程。草稿 MUST 記錄基準發布版本、內容、修訂號與編輯來源；保存或匯入草稿不得直接改變讀者資料。既有 agent 由維護者自行操作，不由網站自動啟動。

#### Scenario: 網站保存與 agent 匯入
- **WHEN** 維護者由表單或檔案匯入修改公司產品定位
- **THEN** 可看到相同的驗證結果、相對基準版本的差異與讀者預覽
- **AND** 未發布前一般讀者仍取得原研究

### Requirement: 版本衝突不得覆寫

草稿更新 MUST 檢查預期修訂號，發布 MUST 檢查基準發布版本。任一基準已改變時 MUST 拒絕覆寫並保留雙方內容，提供可閱讀的差異供維護者處理；不得默默以最後寫入者取代前一份研究。

#### Scenario: 表單與檔案交錯修改
- **WHEN** 表單的草稿修訂已前進，另一份舊檔案仍以舊修訂匯入
- **THEN** 回傳衝突，已保存草稿不被覆寫，舊檔案可另存供比對

#### Scenario: 發布期間基準改變
- **WHEN** 草稿依據的正式版本已被另一個發布取代
- **THEN** 發布不切換讀者版本，要求先整合差異並重新驗證

### Requirement: 驗證後完整發布與可還原

發布 MUST 先完成全體 Schema、引用、關係一致性、資產及預覽驗證，再保存不可變的 Git 內容 commit 與完整讀取投影。只有所有必要產物備妥後才能切換正式版本。失敗 MUST 保留舊版；還原 MUST 指向先前完整版本並保留歷史，不刪除事件或指標修訂。

#### Scenario: 發布一半失敗
- **WHEN** Git 內容已保存但投影建立失敗
- **THEN** 讀者仍取得舊版，維護者可看到失敗階段並重試

#### Scenario: 還原已發布內容
- **WHEN** 維護者選擇先前完整研究版本還原
- **THEN** 地圖、公司、產品及引用一致回到該版，動態指標與事件歷史保留

### Requirement: 重試不產生重複發布

發布與還原 MUST 接受請求識別並支援查詢作業狀態；相同請求及相同內容的重試不得建立重複版本。抓取時間、來源健康與重跑紀錄不得被當成研究實質變更。發布與還原 MUST 保留操作者、基準、結果、內容 commit 與理由。

#### Scenario: 發布回應中斷後重試
- **WHEN** 正式版本已切換但瀏覽器未收到回應，以相同請求識別重試
- **THEN** 取得原作業結果，不重複建立正式版本或更新收藏通知

### Requirement: 維護權限與讀者隔離

系統 MUST 只提供一位維護者的管理登入，不提供讀者註冊。私人網路讀者入口 MUST 不可存取管理畫面、管理 API、草稿或診斷；管理操作仍 MUST 驗證身分與防止跨站請求。研究內容只能修改允許的研究範圍，不能執行任意命令或改寫開發工作目錄。

#### Scenario: 讀者猜測管理路徑
- **WHEN** 未登入讀者由私人網路請求管理頁、草稿或發布 API
- **THEN** 請求被拒絕，且不洩露草稿或內部錯誤

#### Scenario: 惡意研究路徑與內文
- **WHEN** 匯入內容包含路徑穿越、可執行 HTML 或未允許的資產
- **THEN** 驗證拒絕不安全內容，既有研究及程式碼不受影響

### Requirement: 草稿儲存只檢查有變動的內容

儲存或匯入草稿時，系統 MUST 只對新增或內容改變的檔案重做單檔安全檢查。整份草稿層級的界限（大小、檔案數、路徑與資產 hash）MUST 每次都完整檢查。儲存回應時間 MUST 由這次變動的檔案決定，不得隨未改動的檔案數量增加。延遲目標以演練環境經網站同網域 proxy 的量測為準，p95 以每組至少 30 次儲存計算。

#### Scenario: 真實資料只改一份公司文件
- **WHEN** 維護者在真實資料的草稿中以表單修改一份公司文件的摘要並儲存
- **THEN** 儲存成功並產生新修訂，p95 不超過 500 毫秒

#### Scenario: 擴大資料只改一份公司文件
- **WHEN** 草稿為 300 家公司、3,000 條關係的擴大資料，維護者只修改一份公司文件
- **THEN** 儲存的 p95 不超過 1 秒

#### Scenario: 擴大資料修改關係檔本身
- **WHEN** 維護者在擴大資料的草稿中修改 3,000 條關係所在的關係檔
- **THEN** 儲存成功，p95 不超過 3 秒

#### Scenario: 變動的檔案含不安全內容
- **WHEN** 某次儲存只改了一份文件，且該文件含可執行連結、raw HTML 或重複的 YAML 鍵
- **THEN** 儲存被拒絕，已保存的修訂不變，錯誤指出這份文件

### Requirement: 同一修訂的完整驗證結果重複使用

同一份草稿修訂內容的完整驗證 MUST 只在第一次需要時執行；之後對同一修訂的驗證、閱讀預覽與預覽圖解請求 MUST 重複使用該結果。多個請求同時要求同一修訂時，MUST 只執行一次完整驗證。修訂內容一改變，MUST 重新驗證，不得沿用舊修訂的結果。服務重啟後重新驗證即可，不要求保留結果。

#### Scenario: 先驗證再預覽含多張圖解的文件
- **WHEN** 維護者驗證修訂 N，接著預覽一份引用三張圖解的文件
- **THEN** 驗證、預覽與三張圖解請求合計只執行一次完整驗證

#### Scenario: 同一修訂重複驗證
- **WHEN** 已完成驗證的修訂再次被要求驗證
- **THEN** 回傳與第一次相同的結果與內容 hash，回應時間不超過 300 毫秒

#### Scenario: 驗證後再儲存新修訂
- **WHEN** 修訂 N 已通過驗證，維護者儲存修訂 N+1 後再要求驗證
- **THEN** 系統對修訂 N+1 執行完整驗證，不回傳修訂 N 的結果

#### Scenario: 無效修訂的圖解請求
- **WHEN** 修訂未通過驗證，有請求要取得它引用的圖解
- **THEN** 請求被拒絕，且不必為這次請求重新執行完整驗證

### Requirement: 擴大規模的研究可以走草稿流程

草稿流程 MUST 能接受 300 家公司、3,000 條關係規模的研究，且至少保留兩倍的結構餘裕。YAML 結構深度、節點數與 alias 展開 MUST 仍有明確上限；5 MiB 草稿上限不變。超過上限時 MUST 拒絕並指出是哪一份文件。

#### Scenario: 匯入擴大資料
- **WHEN** 維護者以 CLI 匯入 300 家公司、3,000 條關係的擴大資料草稿
- **THEN** 匯入成功，並可完成驗證與預覽

#### Scenario: 結構炸彈仍被拒絕
- **WHEN** 匯入的 YAML 含超過深度上限的巢狀結構，或以 alias 展開超過節點上限
- **THEN** 匯入被拒絕，已保存的修訂不變

### Requirement: 加速不改變驗證與發布的判定

加速後，同一份研究內容 MUST 得到與原本相同的接受或拒絕判定，通過時編譯出的內容 hash MUST 相同。發布前 MUST 仍對全部檔案執行完整驗證，不得因單檔增量檢查而略過。執行環境缺少加速用的解析器時，判定結果 MUST 不變，只允許變慢。

#### Scenario: 兩種解析器的判定一致
- **WHEN** 以加速解析器與原本的解析器分別驗證目前已發布的研究與擴大資料
- **THEN** 兩者的接受結果與內容 hash 完全相同

#### Scenario: 發布仍全面檢查
- **WHEN** 草稿的未變動檔案在先前修訂後才被新的檢查規則判為不合格，維護者要求發布
- **THEN** 發布前的完整驗證拒絕這份草稿，正式版本不切換

### Requirement: 管理頁儲存一次往返即可繼續編輯

儲存草稿的回應 MUST 包含新修訂號、檔案清單與剛儲存文件的表單與完整文字表示，讓管理頁不必再次讀取。選擇草稿時 MUST 只取得修訂摘要與檔案清單，不下載全部檔案內容。完整草稿內容 MUST 仍可透過匯出取得，CLI 匯出與匯入的格式不變。

#### Scenario: 表單儲存後繼續編輯
- **WHEN** 維護者在管理頁按下儲存修訂
- **THEN** 頁面只送出一個儲存請求就顯示新修訂號與更新後的文件，草稿清單中這份草稿的修訂號同步更新

#### Scenario: CLI 匯出不受影響
- **WHEN** 維護者以 CLI 匯出草稿
- **THEN** 取得的交換資料夾與本 change 之前的格式相同，可原樣匯入

### Requirement: 已驗證修訂的閱讀預覽有時間上限

草稿修訂通過驗證後，閱讀預覽一個實體的回應時間 MUST 不超過固定上限：真實資料 p95 不超過 1 秒；300 家公司、3,000 條關係的擴大資料 p95 不超過 3 秒。回應時間包含預覽頁的內容與關係圖，不含圖解檔案。量測以演練環境經網站同網域 proxy 為準，每組資料至少預覽 20 次。加速 MUST 不讓讀者看到未發布的內容：預覽結束後，資料庫不得留下候選版本。

#### Scenario: 真實資料在不同頁面之間預覽
- **WHEN** 真實資料的草稿修訂已通過驗證，維護者在不同實體之間連續預覽 20 次
- **THEN** 每次預覽都成功，p95 不超過 1 秒

#### Scenario: 擴大資料的預覽
- **WHEN** 300 家公司、3,000 條關係的擴大資料草稿已通過驗證，維護者連續預覽 20 次
- **THEN** 每次預覽都成功，p95 不超過 3 秒

#### Scenario: 預覽不留下候選版本
- **WHEN** 一次預覽完成，或預覽途中發生錯誤
- **THEN** 資料庫沒有因此新增任何研究版本或投影資料，讀者取得的正式版本與預覽前相同

### Requirement: 批次投影與逐列投影的結果相同

預覽與發布把研究內容寫入讀取投影時，對同一份研究內容 MUST 產生與逐列寫入完全相同的投影：每張投影表的列、版本識別與內容 hash 都相同，保留的舊歷史紀錄也相同。投影中途失敗時 MUST 不留下部分寫入；發布失敗時 MUST 保留原本的正式版本。

#### Scenario: 兩種寫法逐列比對
- **WHEN** 以目前已發布的研究與擴大資料，分別用逐列寫入與批次寫入投影到各自獨立的測試資料庫
- **THEN** 兩邊每張投影表的列內容完全相同，版本識別與內容 hash 也相同

#### Scenario: 投影途中違反資料庫限制
- **WHEN** 投影途中有一批寫入違反資料庫限制
- **THEN** 整次投影 rollback，沒有留下這次的任何列；若是發布，正式版本不切換，發布作業記為失敗

### Requirement: 管理頁編輯大型文件不會凍結

在管理頁直接編輯文件文字時，從按鍵到下一個畫面的延遲 MUST 不隨檔案變大而失控：近百萬字的關係檔以原始文字編輯，以及一般公司文件以表單編輯，p95 都 MUST 不超過 300 毫秒，最大值都 MUST 不超過 1 秒。量測以演練環境的 headless Chromium 為準，每份文件至少輸入 30 個按鍵。網頁上可編輯的檔案大小 MUST 不因此受到新的限制。

#### Scenario: 原始文字編輯擴大資料的關係檔
- **WHEN** 維護者在管理頁以原始文字打開擴大資料約 97 萬字的關係檔，連續輸入 30 個字元
- **THEN** p95 不超過 300 毫秒，沒有任何一次超過 1 秒

#### Scenario: 表單編輯一份公司文件
- **WHEN** 維護者以表單編輯一份公司文件的研究內文，連續輸入 30 個字元
- **THEN** p95 不超過 300 毫秒，沒有任何一次超過 1 秒
