# industry-map Specification

## Purpose

提供半導體與 AI 伺服器價值鏈的結構化、可遍歷地圖，讓消費端能在不依賴資料庫的情況下，由任一環節推導出受影響的上下游環節與公司，作為事件判讀與題材追蹤的共同基礎。

## Requirements

### Requirement: 環節檔攜帶機器可讀的結構化中介資料

每個環節檔 MUST 在檔案開頭以結構化中介資料區塊宣告該環節的結構，欄位至少包含環節識別碼、中文名稱、所屬層（AI 伺服器或半導體）、價值鏈位置、公司清單、上游環節、下游環節、相關題材、監測指標與觀察訊號。消費端 MUST 能僅讀取該區塊即取得完整結構，無需解析散文。

#### Scenario: 消費端取得環節結構

- **WHEN** 消費端讀取任一環節檔的中介資料區塊
- **THEN** 取得該環節的公司清單、上游環節識別碼與下游環節識別碼
- **AND** 不需解析任何散文段落即可完成

#### Scenario: 缺少必填欄位

- **WHEN** 某環節檔的中介資料缺少任一必填欄位
- **THEN** 結構驗證失敗
- **AND** 錯誤訊息指出該檔案路徑與缺少的欄位名稱

### Requirement: 環節識別碼全域唯一且所有引用可解析

環節識別碼 MUST 在整張地圖中唯一。任何欄位中對環節的引用（上游、下游）MUST 解析到一個既存的環節識別碼。

#### Scenario: 引用不存在的環節

- **WHEN** 某環節的上游或下游列出一個不存在的環節識別碼
- **THEN** 結構驗證失敗並指出來源檔案與該無法解析的識別碼

#### Scenario: 識別碼重複

- **WHEN** 兩個環節檔宣告相同的環節識別碼
- **THEN** 結構驗證失敗並列出兩個衝突的檔案路徑

### Requirement: 上下游關係雙向一致

若環節 A 將環節 B 列為下游，則環節 B MUST 將環節 A 列為上游；反之亦然。地圖 MUST NOT 存在單向宣告的關係。

#### Scenario: 單向宣告的關係

- **WHEN** 散熱環節將 ODM 列為下游，但 ODM 的上游未列出散熱
- **THEN** 結構驗證失敗
- **AND** 錯誤訊息同時指出兩個檔案與缺少的那一側

### Requirement: 公司條目可識別所屬市場

公司清單的每個條目 MUST 包含代號、中文名稱、在該環節中的角色，以及重要性層級。代號 MUST 採可判斷主體類型與所屬市場的形式：台股為四位數字加 `.TW`（上櫃加 `.TWO`），美股為純字母，其他上市市場採該市場標準後綴（如韓國 `.KS`、日本 `.T`、香港 `.HK`），未上市或非上市主體則以 `PRIVATE:` 前綴加識別名。

#### Scenario: 多市場玩家並列於同一環節

- **WHEN** 消費端讀取記憶體環節的公司清單
- **THEN** 能分辨 `000660.KS` 為韓股、`MU` 為美股、`2408.TW` 為台股
- **AND** 每個條目都帶有該公司在此環節的角色描述

#### Scenario: 未上市的關鍵玩家

- **WHEN** 某環節的關鍵玩家未公開上市
- **THEN** 其代號以 `PRIVATE:` 前綴加識別名表示
- **AND** 結構驗證通過，不因無股票代號而被排除

#### Scenario: 代號格式不符

- **WHEN** 某公司條目的代號不符上述任一形式
- **THEN** 結構驗證失敗並指出該條目

### Requirement: 每個環節明確表態市場覆蓋

每個環節 MUST 分別交代台股與美股的主要玩家。若某市場在該環節確實沒有實質玩家，MUST 以明確標記表達，MUST NOT 留空或省略欄位 —— 空白無法區分「尚未填寫」與「該市場無玩家」。若該環節由台美以外的市場主導，MUST 一併列出該市場的主導玩家。

#### Scenario: 台美兩市場皆有實質玩家

- **WHEN** 讀取 ODM 環節
- **THEN** 公司清單同時包含台股與美股條目

#### Scenario: 由第三市場主導的環節

- **WHEN** 讀取記憶體環節，其 HBM 供給由韓廠主導
- **THEN** 公司清單包含韓股主導玩家，且仍交代台股與美股玩家
- **AND** 結構驗證通過

#### Scenario: 單一市場無實質玩家的環節

- **WHEN** 某環節（如 EDA 工具）在台股無實質玩家
- **THEN** 該環節明確標記台股無實質玩家
- **AND** 結構驗證通過，不視為缺漏

### Requirement: 題材檔攜帶生命週期狀態與里程碑

每個題材檔 MUST 宣告題材識別碼、中文名稱、生命週期狀態、涵蓋環節、受惠公司與里程碑清單。生命週期狀態 MUST 取自固定列舉值。每個里程碑 MUST 包含時間、事件與用以確認該事件的證據。

#### Scenario: 讀取題材的受影響範圍

- **WHEN** 消費端讀取液冷題材
- **THEN** 取得其涵蓋環節清單、受惠公司清單與目前生命週期狀態

#### Scenario: 生命週期狀態為非法值

- **WHEN** 某題材的狀態不在固定列舉值之內
- **THEN** 結構驗證失敗並列出允許的值

### Requirement: 題材與環節互相可解析且雙向一致

題材所宣告的涵蓋環節 MUST 解析到既存環節；環節所宣告的相關題材 MUST 解析到既存題材。兩側的關聯 MUST 一致。

#### Scenario: 題材引用不存在的環節

- **WHEN** 某題材的涵蓋環節包含不存在的環節識別碼
- **THEN** 結構驗證失敗

#### Scenario: 關聯只宣告於單側

- **WHEN** 散熱環節列出液冷題材，但液冷題材的涵蓋環節未列出散熱
- **THEN** 結構驗證失敗並指出兩個檔案

### Requirement: 由任一環節可推導影響鏈

給定任一環節識別碼，消費端 MUST 能僅憑地圖檔案推導出受影響的上游與下游環節，以及這些環節中的公司清單，無需任何外部資料來源或資料庫。

#### Scenario: 由事件所屬環節推導下游影響

- **WHEN** 一則事件被歸屬到記憶體環節
- **THEN** 沿下游關係可取得先進封裝、ODM 等受影響環節
- **AND** 取得各環節中的台股與美股公司清單

#### Scenario: 推導在無外部依賴下完成

- **WHEN** 在無網路與無資料庫的環境中執行推導
- **THEN** 僅讀取地圖檔案即可完成，不發生任何外部呼叫

### Requirement: 環節檔的散文段落使用固定標題

每個環節檔 MUST 包含固定的一組段落標題：環節定義、技術變數、玩家格局、傳導鏈、監測指標、風險。消費端 MUST 能據標題擷取特定面向而不需讀完整份檔案。

#### Scenario: 擷取單一面向

- **WHEN** 消費端需要某環節的傳導鏈說明
- **THEN** 能依固定標題定位並擷取該段落

#### Scenario: 缺少必要段落

- **WHEN** 某環節檔缺少任一必要段落標題
- **THEN** 結構驗證失敗並指出缺少的段落

### Requirement: schema 以單一規範文件定義

地圖的結構化欄位與段落規範 MUST 由單一規範文件定義。新增環節或題材時，僅閱讀該規範文件 MUST 足以寫出通過驗證的檔案，不需逆向參考既有檔案。欄位的新增或語意變更 MUST 同步反映於該文件。

#### Scenario: 僅憑規範文件新增環節

- **WHEN** 維護者僅閱讀規範文件後新增一個環節檔
- **THEN** 該檔案通過結構驗證

#### Scenario: 欄位變更未同步規範

- **WHEN** 新增一個必填欄位但未更新規範文件
- **THEN** 該變更視為未完成

### Requirement: 研究投影完整且保留查核基準

網站投影 MUST 保存所有環節、題材、產品、公司與研究頁的完整已發布內容、監測定義、風險、里程碑及證據連結；題材 MUST 顯示原始狀態查核日期，匯入時間不得取代查核日。已發布 Markdown／YAML 的 Git commit MUST 為正式研究來源，網站表單只編輯待發布草稿；動態事件及財務不寫入靜態監測定義。

#### Scenario: 匯入既有題材
- **WHEN** 重跑題材匯入
- **THEN** 全文與連結保留，狀態查核日期不被改為匯入日

#### Scenario: 網站與檔案編輯同一研究
- **WHEN** 兩種編輯方式各自完成發布
- **THEN** 都能由已發布內容 commit 重建相同研究投影，草稿不被誤作正式來源

### Requirement: 題材結構化判讀與原研究一致

題材 MUST 能攜帶結構化判讀、支持／反向論點、條件、缺口、下一確認點、傳導假設與里程碑核對。研究及判讀 MUST 以 Markdown 為唯一來源，結構化查核日 MUST 與散文查核基準一致；既有全文、狀態及預期里程碑不得被匯入時間取代。舊檔無新增欄位 MUST 仍能驗證及讀取。

#### Scenario: 舊格式與新增判讀並存
- **WHEN** 地圖包含舊格式題材及已有結構化判讀的題材
- **THEN** 舊格式仍可讀；新增內容通過結構檢查並保留全文與原查核基準

### Requirement: 判讀引用可解析且範圍明確

結構驗證 MUST 檢查論點／證據／里程碑識別唯一、來源及環節引用可解析、傳導步驟符合宣告關係、支持程度與影響方向合法、必要來源位址及期間欄位格式正確。缺口與未知日期 MUST 可以明確表示；結構通過不得被宣稱為內容正確性已驗證。

#### Scenario: 無法解析的證據或傳導步驟
- **WHEN** 某判讀引用不存在的來源、論點、里程碑或不成立的結構步驟
- **THEN** 驗證失敗並指出題材檔案與相應欄位

### Requirement: 指標定義與動態觀測分離

題材 MUST 能引用可解析的指標定義；動態觀測數值 MUST 保存於資料層，地圖的 kpis／signals 仍記錄要觀察的項目。資料期別、原始摘錄與里程碑核對可作研究基準，但不得用靜態示範值充當持續更新的指標。

#### Scenario: 指標更新與地圖重跑
- **WHEN** 同一指標取得新期觀測並重跑地圖匯入
- **THEN** 地圖研究與查核基準不被數值更新覆寫，既有觀測仍保留

### Requirement: 結構關係攜帶型別與成立條件

地圖 MUST 能為有向關係宣告供應或需求回饋型別、供應項目或需求機制、介面依賴、適用條件、證據程度、證據及缺口。關係說明 MUST 對應已宣告的下游邊，且每條邊只有一份權威說明；原上下游雙向一致規則 MUST 保留。缺少舊格式說明時 MUST 明示尚未核對，不得一律當成已核實供應。

#### Scenario: 需求回饋仍屬真實回路
- **WHEN** 地圖宣告資料中心至運算晶片為需求回饋
- **THEN** 消費端可取得型別與需求形成條件，原上下游引用仍雙向一致
- **AND** 不為了區分型別刪除回路或使原影響範圍不可達

#### Scenario: 關係說明引用不存在的邊
- **WHEN** 說明指向未在下游宣告的環節、重複定義同一邊或引用不存在的證據
- **THEN** 驗證失敗並指出檔案與對應欄位

### Requirement: 技術論述區分產品邊界與採用證據

環節及題材 MUST 能宣告產品或技術邊界、採用條件、瓶頸、替代限制、技術論述及證據缺口。論述 MUST 有穩定識別、證據程度與來源定位；規格要求、廠商能力、客戶採用及收入證據 MUST 可分辨。沒有足夠證據的面向 MUST 明列待核實，不得以常識、規範存在或同環節公司名單代替。

#### Scenario: 比較冷板與設施冷卻角色
- **WHEN** 研究列出冷板、歧管、CDU 及設施水路
- **THEN** 各自產品邊界、整合依賴及限制可回溯至相應論述或明示缺口
- **AND** 規格相容不被當成特定公司已取得客戶量產訂單

#### Scenario: 先進封裝的替代條件
- **WHEN** 研究比較晶圓／面板加工、中介層與載板方案
- **THEN** 說明各技術層次、替代成立條件及仍缺少的證據，不把不同層次寫成必然互斥

### Requirement: 全圖研究可核對且按優先序補強

本 change 的研究交付 MUST 先完成散熱、電力、互連、網路與先進封裝，再完成其餘環節。現有 17 個環節及 7 個題材 MUST 都能閱讀技術邊界、條件、瓶頸、替代限制及證據缺口，並具查核基準及可讀來源或具體取得限制。保留六個固定環節段落、原始全文及題材判讀；動態指標值 MUST 不寫回 kpis／signals。

#### Scenario: 缺少可公開取得的技術證據
- **WHEN** 某環節的特定技術限制只能找到不可公開取得的文件
- **THEN** 該面向列出具體缺口與待確認文件，既有研究仍可閱讀
- **AND** 不以 fixtures、其他產品規格或無來源敘述補成已完成核實

### Requirement: 擴充 schema 保持舊格式與原子匯入

新增欄位 MUST 在唯一 schema 文件中定義合法值、必要引用及範例。舊地圖缺少擴充欄位 MUST 仍可驗證、讀取及離線執行三種遍歷；新增資料不合法時 MUST 拒絕整次匯入，保留原投影。結構驗證結果 MUST 不被宣稱為內容正確性查核。

#### Scenario: 舊格式與新版混用
- **WHEN** 地圖同時含未補技術欄位的舊檔與新檔
- **THEN** 舊檔維持可讀，新增引用及型別依 schema 驗證，覆蓋資訊明示未補面向

#### Scenario: 新版資料有非法引用
- **WHEN** 匯入含失效文件版本或不合法關係說明的地圖
- **THEN** 整次匯入失敗，既有研究、題材版本、事件、觀測與關注更新基準不變

### Requirement: 應用與產品分類可解析且有明確邊界

研究 MUST 能以結構化資料表達應用、供應角色／子領域、產品、技術、公司及其關聯；產品與供應角色 MUST 記錄定義、用途、邊界、採用條件、瓶頸及替代限制。分類父子關係不得有環，供需及需求回饋圖可保留真實回路；所有引用 MUST 可解析。

#### Scenario: 從液冷用途辨識供應角色
- **WHEN** 讀取液冷相關產品分類
- **THEN** 可分辨冷板、歧管、CDU 與連接組件的不同交付內容，並連到對應公司與技術說明

#### Scenario: 分類與供需回路分別驗證
- **WHEN** 分類父子形成環，或供需圖形成既有資料中心需求回饋
- **THEN** 前者被拒絕，後者可通過且遍歷能終止

### Requirement: 穩定公司身分與上市代號分離

新版研究 MUST 使用不隨名稱或上市代號變更的公司身分，另保存市場、上市代號、中文／英文別名及官方識別。不同市場同一法律主體可對應同一公司，母子公司不得只因名稱相似而合併。舊 ticker 與 PRIVATE 識別 MUST 保留可解析映射，未上市公司不得捏造 listing。

#### Scenario: 跨市場與未上市公司
- **WHEN** 研究同一公司的不同上市證券，或讀取 Boyd
- **THEN** 公司研究不因證券代號重複建立，未上市公司也能被引用且不顯示虛假股票代號

### Requirement: 關係依證據區分能力與具名供應

每條公司／產品關係 MUST 表達型別、方向、交付產品或機制、適用條件、證據程度、查核基準與來源定位。供應能力、具名供應、合作、競爭及需求回饋 MUST 分開；具名供應需有對應交易或採用證據，不得由產品相容、共同題材或匿名客戶推定。新增公司關係只維護一筆事實，反向查詢不得要求人工重複輸入。

#### Scenario: 只有產品能力證據
- **WHEN** 公司官網僅證明能供應高速連接器，沒有公開客戶
- **THEN** 可建立公司與產品的能力關聯，不建立對特定客戶的已證實供應關係

### Requirement: 主張與來源界線可追溯

研究主張 MUST 區分 well-supported、inference、needs-verification，並可連到支持／反向證據、適用期間與引用位置。文件為正式規範、草案、路線圖或廠商說明的性質 MUST 保存；文件更新不自動改寫研究或提升確定性。無法公開確認的客戶或數值 MUST 明示限制，不補造內容。

#### Scenario: 草案技術被報導為量產
- **WHEN** 唯一已讀來源是草案規格或廠商路線圖
- **THEN** 不得據此把客戶採用或量產收入標為已證實，引用保留文件性質與範圍

### Requirement: 術語圖解與技術比較有研究脈絡

術語頁 MUST 提供中文解釋、原創或可使用的示意圖、適用範圍、相關產品／公司及來源；技術比較 MUST 交代比較條件與限制，不宣稱不同使用情境的技術必然可替代。圖解資料與資產引用 MUST 可驗證，並由同一 Schema 規範文件定義。

#### Scenario: 比較光互連與銅互連
- **WHEN** 讀者從產品頁進入相關術語或技術比較
- **THEN** 可理解距離、速率、功耗及成本條件，並返回對應產品研究與證據

### Requirement: 應用的閱讀流程欄位可驗證

應用 MAY 宣告讀者問題與流程步驟；每個步驟 MUST 有標籤，引用的產品 MUST 存在且屬於該應用的分類之下。這些欄位只描述閱讀順序，不構成研究主張或供應關係；驗證失敗 MUST 拒絕發布。

#### Scenario: 步驟引用其他應用的產品
- **WHEN** 流程步驟引用不在該應用分類下的產品
- **THEN** 驗證拒絕並指出應用與產品
