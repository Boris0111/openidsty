# Spec Delta

## ADDED Requirements

### Requirement: 正式服務只執行已合併提交的版本化 image

正式研究服務 MUST 只執行由主線（`main` 的第一父鏈）上的提交、直接自版本控制內容建置的 image；每個 image MUST 標示來源提交，每個運行容器的 image 與提交 MUST 可查詢並與部署紀錄一致。開發用 checkout 的分支切換、未提交修改與測試檢查 MUST NOT 改變正式服務的 image、容器、祕密、備份或排程。會改變正式服務的操作 MUST 只在指定的部署目錄、工作目錄乾淨且版本與部署紀錄一致時執行，否則拒絕並說明原因；正式資料庫已存在時 MUST NOT 產生新的執行祕密。

#### Scenario: 開發 checkout 切換分支
- **WHEN** 維護者或 agent 在開發 checkout 切換分支、留下未提交修改，並執行測試與檢查
- **THEN** 正式服務的 image、容器、祕密、備份與排程都不變

#### Scenario: 部署未合併的提交
- **WHEN** 要部署的提交不在 `main` 的第一父鏈上，例如未 merge 的分支或 PR 內部的中間提交
- **THEN** 部署拒絕並說明原因，正式服務維持原版本

#### Scenario: image 內容與版本控制一致
- **WHEN** 從某個提交建置正式 image
- **THEN** image 內的專案檔案與該提交的版本控制內容逐位元組相同，不受換行轉換或未追蹤檔案影響
- **AND** image 標示來源提交、資料庫遷移的最新版本與其中的收縮遷移

#### Scenario: 在部署目錄外操作正式服務
- **WHEN** 在部署目錄以外、部署目錄有未提交修改或未追蹤檔案，或其版本與部署紀錄不一致時，執行會改變正式服務的操作
- **THEN** 操作拒絕並指出不符合的條件，正式服務不變

#### Scenario: 缺少正式祕密時不產生新祕密
- **WHEN** 正式資料庫的 volume 已存在，而執行位置沒有正式祕密設定
- **THEN** 操作拒絕，不產生與既有資料庫不符的新祕密

#### Scenario: 查詢運行版本
- **WHEN** 維護者查詢正式服務狀態
- **THEN** 列出每個運行容器的提交與 image、資料庫遷移版本與最近一次部署紀錄，並指出不一致之處

### Requirement: 部署與回退先備份並留有紀錄

每次部署與回退 MUST 先完成可核對的備份，並在只追加的部署紀錄寫入一筆，包含提交、image、遷移版本前後、備份位置、smoke 結果與成敗。部署 MUST 在新版本的初始化成功後才替換服務，並替換所有運行中的應用服務。smoke 失敗時 MUST 記錄並回報可執行的回退方式，或說明為何只能還原備份，不自動回退。回退 MUST NOT 重新執行初始化；跨越收縮遷移或排程元件版本時 MUST 拒絕並指向備份還原。部署、回退與每日備份 MUST NOT 同時執行。

#### Scenario: 標準部署
- **WHEN** 維護者部署一個主線提交
- **THEN** 先完成備份，新版本初始化成功後才替換 API、網站與運行中的排程服務
- **AND** smoke 檢查結果、每個服務的 image 與遷移版本寫入部署紀錄

#### Scenario: 新版本初始化失敗
- **WHEN** 新版本的資料庫遷移或研究初始化失敗
- **THEN** 原版本的服務繼續回應讀者，部署紀錄寫入失敗原因

#### Scenario: 部署後 smoke 檢查失敗
- **WHEN** 服務已替換，但健康檢查、已發布研究版本或頁面檢查不通過
- **THEN** 部署紀錄標示失敗，並列出可直接執行的回退指令，或說明因收縮遷移只能還原備份
- **AND** 系統不自動回退

#### Scenario: 回退到只差擴充遷移的前一版
- **WHEN** 維護者回退到部署紀錄中前一個成功版本，兩者之間只有擴充遷移
- **THEN** 回退不執行初始化與地圖重新匯入，不因舊版不認得較新的遷移版本而失敗，也不新增判讀版本
- **AND** smoke 通過後寫入部署紀錄

#### Scenario: 回退跨越收縮遷移或排程元件版本
- **WHEN** 回退的目標版本與目前資料庫之間有收縮遷移，或兩者的排程元件版本不同
- **THEN** 回退拒絕，指出原因及作為回退邊界的部署前備份

#### Scenario: 部署時有資料更新正在執行
- **WHEN** 部署開始時排程中的資料更新仍在執行，或每日備份正在進行
- **THEN** 部署拒絕或等待鎖釋放，不與它們同時寫入；維護者明確強制時才中斷正在執行的資料更新

### Requirement: 資料庫遷移區分擴充與收縮

每個資料庫遷移 MUST 屬於擴充（前一版程式可在新 schema 上運作）或收縮（移除、改名、收窄既有結構或刪除資料）。含破壞性語句的遷移 MUST 標記為收縮，或附上前一版不受影響的審查理由；自動檢查 MUST 拒絕未標記者，並 MUST 要求遷移鏈線性且只有一個 head。收縮遷移 MUST 在前一個已部署版本不再使用被移除的結構後才部署，部署時 MUST 明確確認，該次部署前備份為回退邊界且 MUST NOT 被例行清理刪除。已合併的遷移 MUST NOT 刪除或改寫，撤回以新的遷移進行。

#### Scenario: 新增未標記的破壞性遷移
- **WHEN** 有人新增含刪除資料表、欄位、政策或資料，或改名、收窄型別的遷移，但未標記
- **THEN** 自動檢查失敗，指出檔案與語句

#### Scenario: 經審查的擴充遷移
- **WHEN** 遷移只新增結構，或含可疑語句但已附上前一版不受影響的理由
- **THEN** 自動檢查通過，該遷移不構成回退邊界

#### Scenario: 部署含收縮遷移
- **WHEN** 要部署的版本相對目前資料庫新增收縮遷移，而維護者未明確確認
- **THEN** 部署拒絕並列出收縮遷移
- **AND** 明確確認後部署，該次部署前備份標示為回退邊界，例行清理不刪除它

#### Scenario: 遷移鏈分岔
- **WHEN** 兩個遷移宣告同一個前一版本，或遷移編號與檔名不一致
- **THEN** 自動檢查失敗並指出衝突的遷移

### Requirement: 合併前實機驗證在演練環境進行

需要實機的合併前驗證 MUST 在獨立的演練環境進行，MUST NOT 讓正式服務執行未合併的程式碼。演練 MUST 先以備份記錄的基準 image 從最新正式備份還原，再以待合併提交的 image 預演部署與回退，並核對資料差異。分支程式的資料庫契約檢查與重建檢查 MUST 只寫入演練環境的資料庫與 volume。演練 MUST 可從任何 checkout 或 worktree 執行而不讀取正式祕密，錯誤輸出 MUST 遮蔽演練祕密。只有正式環境才有的行為於合併後部署時核對並記錄。

#### Scenario: 預演 PR 的部署
- **WHEN** 維護者從 PR 的 worktree，以最新正式備份還原演練環境，再部署 PR 提交的 image
- **THEN** 演練以與正式部署相同的步驟完成初始化與 smoke 檢查，報告列出資料表的變動與遷移版本
- **AND** 正式服務的 image、容器、資料與祕密都不變

#### Scenario: 待合併版本含新遷移
- **WHEN** PR 新增資料庫遷移，維護者從正式備份還原演練環境
- **THEN** 還原使用備份記錄的基準 image 而成功，新遷移只在預演部署時套用

#### Scenario: 預演回退
- **WHEN** 預演部署後回退到基準 image
- **THEN** 只差擴充遷移時回退通過 smoke 檢查；跨越收縮遷移時回退被拒絕，與正式環境的規則相同

#### Scenario: 從 worktree 執行演練
- **WHEN** 在沒有正式祕密的 worktree 執行演練，且某個步驟失敗
- **THEN** 演練不讀取正式祕密，錯誤輸出中的演練祕密已被遮蔽

#### Scenario: 分支程式的資料庫檢查
- **WHEN** 以分支程式執行需要 PostgreSQL 的契約檢查或研究重建檢查
- **THEN** 檢查只寫入演練環境的資料庫與 volume，正式資料庫 cluster 與 volume 不變

## MODIFIED Requirements

### Requirement: 開發與維護操作可驗證

README MUST 提供前後端開發、容器啟動與停止、單次資料更新、測試、日誌、來源狀態、備份還原、正式服務部署與回退、部署紀錄查詢及公開部署步驟；專案 MUST 提供 dev server 啟動設定。

#### Scenario: 執行單次更新與備份
- **WHEN** 維護者依文件執行更新、備份與還原
- **THEN** 能查詢更新結果，且在獨立還原環境核對資料，不覆寫其他專案

#### Scenario: 依文件部署與回退
- **WHEN** 維護者依文件把一個主線提交部署到正式服務，之後回退到前一版
- **THEN** 每一步都有對應指令與預期結果，部署紀錄可查到兩次操作的提交、備份與 smoke 結果

### Requirement: 自動檢查與 runtime 一致

自動檢查 MUST 使用與 runtime image 相同的鎖定 Python 依賴版本，不得在檢查時解析出不同的間接依賴。測試 fixtures 在任何平台 checkout 後 MUST 與版本控制中的位元組內容一致，不得因換行轉換改變內容或雜湊。版本控制中的 runtime 與維運腳本測試 MUST 納入自動檢查，包括研究服務的部署、回退與資料庫遷移分類規則；需要 Docker、真實資料庫或外部來源的檢查仍與自動檢查分開。

#### Scenario: Windows checkout 執行雜湊測試
- **WHEN** 在預設會轉換換行的 Windows checkout 執行依賴 fixture 雜湊的離線測試
- **THEN** fixture 位元組與版本控制內容相同，測試結果與 Linux checkout 一致

#### Scenario: 間接依賴發布新版
- **WHEN** 某個未直接鎖定的間接依賴在套件庫發布新版
- **THEN** 自動檢查仍安裝 runtime 使用的版本，不因新版而產生與 runtime 不同的結果

#### Scenario: 維運腳本測試
- **WHEN** 有人修改研究服務的啟動、互斥、設定檢查、部署或回退腳本，或新增資料庫遷移
- **THEN** 自動檢查執行對應的測試，不需要 Docker 也能驗證設定規則、部署順序、回退的拒絕條件與遷移分類
