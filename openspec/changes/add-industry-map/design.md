# Design

## Context

動機見 `proposal.md` 的 Why；行為契約見 `specs/industry-map/spec.md` 與 `specs/information-sources/spec.md`。本文只說明架構取捨。

形塑本設計的既有條件：

- 專案為全新 repo，零應用程式碼，無既有慣例需要遷就。
- 已確立的交付形態是 **repo 內結構化 Markdown ＋ Claude Code skill**，無伺服器、無資料庫、無排程。這排除了任何需要常駐服務的方案。
- 本機已具 Python 3.12 與 PyYAML 6.0.1，無需新增安裝。
- 分析框架沿用既有的 `industry-quick-research` skill（商業模式／營收結構／成長動能／終端市場／客戶／護城河／管理層指引），不另造一套。
- **最硬的約束**：後續的消息流 change 會消費本次的欄位結構。schema 一旦被消費即具契約性質，因此結構正確性的優先級高於內容豐富度。

## Goals / Non-Goals

**Goals:**

- 讓「給定一則事件 → 推導受影響環節與公司」在**只讀純文字檔**的條件下可完成。
- 結構（可被程式遍歷）與解釋（供人閱讀判斷）在同一份檔案中分離承載，避免兩份資料不同步。
- 交叉引用的錯誤在**撰寫時**就被攔下，而不是在後續 change 消費地圖時才炸開。

**Non-Goals:**

- 不追求市佔率等數字的精確性。地圖承載的是**結構與關係**，數字只作為量級參考。
- 不納入財報數據、股價、估值。這些有專門來源，複製進地圖只會過時。
- 不建立嚴格的拓樸排序或有向無環圖。真實供應鏈存在回路（電源同時供應 ODM 與資料中心），強求 DAG 會逼出失真的結構。
- 驗證器不檢查內容正確性 —— 不驗證某公司是否真屬於某環節、市佔是否正確。那是人的判斷，不是程式能裁決的。

## Decisions

### 以 YAML frontmatter 承載結構，而非資料庫

**選擇**：每個環節／題材檔以 YAML frontmatter 宣告結構化欄位，其後以 Markdown 散文解釋。

**為何**：消費端需要機器可讀，但交付形態明確排除了基礎設施。Frontmatter 同時滿足三件事：可被程式解析、可被 git diff 審閱、可被人直接編輯。純文字也讓地圖的演進歷程留在 git 歷史裡。

**替代方案**：

- *SQLite 或 JSON 資料檔*：查詢更強，但引入了「資料」與「說明」兩份需手動同步的東西，且 diff 不可讀。對一張 17 環節的地圖，查詢能力不是瓶頸。
- *純散文 Markdown*：人讀最舒服，但消費端得靠 LLM 每次重新解析散文來推導傳導鏈，結果不穩定且不可驗證。這正是「先建地圖」要避免的坑。

### 檔案粒度為環節，而非公司

**選擇**：一個價值鏈環節一個檔案，公司作為環節內的條目。

**為何**：消息判讀的單位是環節。「記憶體漲價」要先定位到環節，才能談哪些公司受影響。環節的數量與邊界遠比公司清單穩定 —— 公司會進出、改名、被併，環節不會。

**替代方案**：*一公司一檔*會讓傳導鏈散落在數十個檔案中，且同一條上下游關係需在兩個公司檔重複描述。個股深度檔留給後續 change，屆時以 ticker 連回環節。

### 台美與第三市場並列同檔，不按市場分目錄

**選擇**：同一環節的台股、美股、以及該環節的第三市場主導者（韓、日）列在同一份環節檔的公司清單中。

**為何**：判讀傳導鏈時必須同時看到上游與下游，而這兩端往往跨市場 —— 上游是美系或韓系大廠，下游是台廠。按市場分目錄會讓每次判讀都要開兩三個檔案再自行拼接，且無法在單一檔案內表達「誰供應誰」。

**替代方案**：*`tw/` 與 `us/` 分家*在維護分工上較清楚，但把判讀時最需要的鄰接資訊切開，代價遠大於好處。

### 上下游雙向顯式宣告，由驗證器保證一致

**選擇**：A 宣告 downstream 含 B，同時 B 必須宣告 upstream 含 A。

**為何**：消費端常只讀單一環節檔（例如判讀一則特定環節的新聞）。若 upstream 需由全圖推導，就得先掃過所有檔案才能回答「誰供應我」，這讓單檔讀取失去意義。

**取捨**：這是刻意引入的冗餘，違反 DRY。代價是手寫易漏，因此由驗證器強制雙向一致 —— 用自動檢查換取讀取端的簡單性。

**替代方案**：*只宣告單向、另一向由程式推導*較不易寫錯，但把成本轉嫁給每一次讀取，且要求消費端必須有能力掃全圖。

### 環節邊界以「可替換的供應角色」裁定

**選擇**：切分依據是「這群供應商在系統中扮演一個可彼此替換的角色」，而非依公司、依技術名詞、或依財報分類。

**為何**：邊界需要一條可重複套用的裁決規則，否則新增環節時會各憑直覺，地圖逐漸失去一致性。散熱與電源分屬不同環節，因為供應商不互相替換；氣冷與液冷同屬散熱，因為多數玩家同時供應兩者且客戶會在兩者間切換。

**後果**：同一家公司可以出現在多個環節（鴻海既是 ODM 也做連接器），以各環節內的角色欄位區分。驗證器因此**不**禁止 ticker 跨檔重複。

### `position` 為粗略序位，不保證無環

**選擇**：以整數表達在價值鏈上的大致位置供排序與方向感，但明確不保證整張圖無回路。

**為何**：真實供應鏈有回路。電源供應 ODM，也直接供應資料中心；資料中心的資本支出又回頭驅動運算環節。若要求嚴格分層，必然得砍掉真實存在的關係。

**後果**：消費端沿上下游遍歷時必須自行處理環路（記錄已訪問節點）。這一點需寫入規範文件，否則後續 change 會寫出無限迴圈。

### 以代號作為公司的正規識別鍵

**選擇**：代號為公司在地圖中的唯一鍵，格式同時編碼市場歸屬；未上市主體以 `PRIVATE:` 前綴表達。

**為何**：中文名有別稱（台積電／TSMC／2330 指同一間），用名稱當鍵會在跨檔引用時對不上。代號唯一、穩定，且能銜接外部資料。

**為何需要 `PRIVATE:`**：部分環節的關鍵玩家並未上市（例如散熱的 Boyd）。若格式只容許上市代號，這些玩家會被迫排除，地圖就會在這些環節失真。

### 題材狀態採固定列舉

**選擇**：`emerging` / `validating` / `scaling` / `mature` / `fading` 五態。

**為何**：後續的題材追蹤需要據狀態排序與篩選（「哪些題材剛進入 validating」）。自由文字無法比較。五態對應的是**證據強度**而非時間 —— 從「有人在談」到「有訂單與財報佐證」，這正是題材判讀最需要區分的維度。

### 驗證器使用 Python 加 PyYAML，只驗結構

**選擇**：單一 Python 腳本，依賴 PyYAML。

**為何**：本機已具備兩者，零安裝成本。YAML 的邊角（中文、冒號、引號、多行）用手寫 parser 必然出錯，而 PyYAML 已正確處理。腳本只做結構檢查：必填欄位、識別碼唯一性、引用可解析、雙向一致、代號格式、列舉值、段落標題齊備。

**替代方案**：*手寫極簡 parser 以求零依賴*會在含冒號的中文角色描述上立刻失敗；*Node 加 yaml 套件*需另裝依賴，無優勢。

## Risks / Trade-offs

- **地圖內容隨時間失真** → 欄位設計成記錄「要看什麼指標」而非「指標現在是多少」。易過時的數字一律不進地圖，動態資訊由後續的消息流 change 負責。
- **手寫雙向引用必然漏寫** → 驗證器強制檢查，並列為每批環節撰寫完成後的必跑步驟，而非留到最後一次性驗。
- **schema 被後續 change 消費後再改成本高** → 交付前必須以 2–3 則真實近期新聞手動走一遍傳導鏈（對應「由任一環節可推導影響鏈」需求）。走不通就改 schema，不要先往下做。這是本次最關鍵的驗收動作。
- **環節邊界的主觀性** → 裁決規則寫入規範文件。邊界爭議一律回到「是否為可彼此替換的供應角色」，而非訴諸個人判斷。
- **遍歷時遇到環路** → 規範文件明示圖可能有環，消費端須記錄已訪問節點。
- **`sources.yaml` 的 RSS 位址會失效** → 每筆帶可達性狀態與查核日期，失效者標記為未驗證而非刪除或靜默留下死連結。

## Migration Plan

無遷移需求：全新目錄、無既有資料、無既有消費端。回滾為刪除新增目錄即可。

## Open Questions

- 未上市主體的 `PRIVATE:` 識別名目前自由命名。若數量成長到難以辨識重複，再補一份命名對照表。不影響 schema 或消費端。
- `sources.yaml` 各筆 RSS 的實際可用性需在撰寫時逐一確認。結果只影響該筆的可達性標記，不影響結構。
